# バージョン管理ツール、どれを使えばいいのか

日頃 `brew` や `npm` 、　`pip` などメジャーなバージョン管理ツールを使う中で複数ツールにおいてバージョンが衝突した時どう整理されるべきなのかわかっていなかったのでまとめた。

厳密にはバージョン管理ツールではないものもあるが、そういうことではない。
厳密に棲み分けだすとそれぞれのツールは複合的な機能を持ったツールになっており、それ故にややこしい。

大筋の理解と今後の方針を考える際の一助となる情報としてまとめる。

# 結論

バージョン管理ツールを見る時は役割とスコープの二軸で見るとおおよそ立ち位置が整理できそうだった。

# 役割

バージョン管理ツールの目的を示す。

一つのツールが複数の目的を持っていたり、前述の通りそもそもバージョン管理ツールではないものもあるが理解促進のために割り切って書いた。

![バージョン管理ツールの棲み分け - visual selection.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/634043/0fb24555-956c-47fc-a555-0f3d4809f0aa.png)


## ツール配布

Macであればbrew, nix、Windowsであればwget, chocolatey, scoopなどを指す。

端末にインストールするユーティリティ系ツールや、asdf, miseといった言語・ランタイムそのものを管理するツールを入れる。

これはグローバルにいれるツールなので、開発プロジェクト固有のツールはbrewやwgetを通して入れない。

## ランタイム切替

asdf, mise、言語固有のものであればnvmやpyenvなどを指す。

nodeやpythonといった言語、ランタイムそのものを入れる。

複数バージョン入れておき、プロジェクトごとに言語やランタイムのバージョンを制御する。

## パッケージバージョン固定（開発用CLIバージョンを固定）

開発で使いたいCLIなどを指す。

これも基本的にはasdfやmiseなどで管理しておくのが良さそう。
npxやpipxなどローカルの実行ファイルを参照しない形であれば問題ないが、npxなどはローカルに該当ファイルがあればそれを呼び出して実行するので注意が必要。

開発チームでAWSの構築もやるような小規模な案件ではaws-cliのバージョン管理が疎かになっているプロジェクトを見かける。
というか過去の自分がそういうおざなりな管理をしていた。

## 依存解決・ロック

npm, pipといったいわゆるパッケージマネージャー（パッケージレジストリのCLIツールであることが多い気がする）と呼んでいるもの。
パッケージのバージョン管理をおこなう。

プロジェクト固有のライブラリをインストールし、lockファイル（package-lock.jsonやrequirement.txt）として出力することで開発者間でのライブラリのバージョン差異をなくす。

表から記載漏れてしまったが、リンター、フォーマッター、モノレポ管理ツールなどはここに属されるだろう。


## 仮想環境（プロジェクト分離）

これは他の役割のツールと違いバージョン管理ツールではないが、よく混乱するので含めた。

コンテナのように環境を独立させ環境の前提を揃える。
これによりどんなに汚染された環境でも、全員同じ開発環境を作ることができる。


# スコープ

そのツールがどこまでの影響範囲を想定しているかを示す。

あくまで想定なのでbrewを使わず `npm install -g` でほしいツールを入れる、と言ったこともできてしまう。

![バージョン管理ツールの棲み分け - visual selection (1).png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/634043/e83cbd75-b63d-4359-bf90-bc6bf13a158e.png)


## 端末

端末全体でバージョン管理したいもの。
brewでインストールしたasdfやnvm自体は端末全体で一意なバージョンとなる。


## プロジェクト

開発するプロジェクトごとにバージョン管理が必要なもの。

プロジェクトの単位はプロダクトではなく更に開発領域ごと（ウェブフロントエンド、モバイル、バックエンド、インフラ、バッジ、ジョブ...など）にバージョン管理する必要がある。

## ジョブ（一時的な使用）

プロジェクトに関するもので、開発の任意のタイミングで実行するもの。
マイグレーションツールやデプロイツールなど。

これはプロジェクトのスコープに含めてバージョンを固定してしまってもいいと思うが、この辺はチームのルール次第。

# 疑問

## npmやpipでグローバルインストールしてはダメか？

時々サンプルなどで `npm install -g ..`といったコマンドを見かけるが、上記のようにプロジェクトごとにバージョンをしっかり管理したり、仮想環境やコンテナで環境を独立させているなら別に問題はないと思う。

ただ個人でちょっと何か動かしたいとか、特に上記ジョブ（一時的な使用）スコープのツールを動かすときに思わぬつまづきに繋がったりするので極力避けたい。

## 結局どのツールを使えばいいのか？

先程の表と同じだが、非推奨なものは消した。
この中から役割ごとに一つずつ ①個人で遊ぶ ②開発プロジェクトで使う ツールを選んでいけば良さそう。


![バージョン管理ツール整理2.drawio.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/634043/14d3bc8d-47cd-4934-a4db-8d600367d4c5.png)


特に ①個人で遊ぶ の方が何も考えずに手を動かしたGet Startedなどに侵され無法になりがちなので、この辺をしっかり抑えつつ業務や個人の開発でも管理方法を整理しておけば良さそう。

情報の枯さ具合で考えるなら `brew` + `asdf` + `${依存解決・ロック}` + `Docker` の構成にしておくのが良さそう。


個人的な関心度で言うとbrewの代わりにNix使う筋は良さそうに見える。

brewでは環境お引越しの際に `brew bundle dump` して実行時点のパッケージ一覧を出力し、それを元に移行先で再構成する必要がある。

一方Nixはlockファイルを生成しているのでgitでバージョン管理ができるようです。
https://zenn.dev/thinceller/scraps/28fa74d29d8df7

Nixは他にも以前関係の衝突が原理的に発生しないとか、Nix言語による再現性の保証とか色々売り文句はあるようですがここではこれ以上の深追いは止めておきます（よくわかっていない）。
https://zenn.dev/asa1984/books/nix-introduction/viewer/03-why-use-nix

役割とスコープの観点で見ればバージョン管理ツールの立ち位置が理解しやすくなると思う。
